    The Basics

    Booqable apps are modular extensions that add new functionality to a Booqable account or its online store. They're built by third-party developers and distributed through the App Store, where merchants discover, install, and manage them.

    An app is fundamentally one file — a booqable.json manifest — plus whatever templates, assets, and backend code it needs. Depending on what your app does, it can:

    • Add an analytics/marketing script — see Tracking Scripts
    • Add custom content blocks to the website builder — see Theme Blocks
    • Offer custom shipping rates at checkout — see Delivery Carriers
    • Process payments, authorizations, or refunds — see Payment Options
    • Embed a full page or dashboard inside Booqable — see Embedded Pages
    • Show a panel next to an order, customer or product — see Sidebar Frames

    An app can combine more than one of these — the example payment app on GitHub shows a complete OAuth + payment-options + embedded-page integration if you want a working reference to read alongside these docs.

    App Manifest

    Every app ships a booqable.json manifest at its root — the one file Booqable requires. Alongside it, an app includes whatever templates, assets, and locale files it needs:

    app-name/
├── booqable.json          # required, at the app's root
├── assets/                # convention
├── config/
│   └── locales/           # required: *.yaml, one per locale
└── templates/             # convention, only if you declare
                            # tracking_script or theme_blocks

    Files are referenced from booqable.json by their exact relative path — organize them however makes sense for your app. Folders like assets or templates are common conventions, not requirements. The one structural rule besides booqable.json itself: locale files live under config/locales/ as .yaml files (e.g. en.yaml, pt_BR.yaml). The top-level key in each file (en:) defines its locale, and every localization key you use must exist in every locale file.

    booqable.json is validated against a versioned JSON Schema, declared by its own $schema field — see Reference for the exact current shape.

    Settings UIs, plan pricing, and locale file content are covered in depth in Configuration.

    App Store Listing

    Your app's store listing — the card in the App Store, its detail page, and its plan picker — is built entirely from fields in booqable.json's app_store object and plans array:

    • title — shown on the listing card and detail page. Required.
    • description.short — shown on the listing card. Required.
    • description.long — shown on the detail page. Required.
    • categories — drives listing filters and detail-page pills.
    • icon — shown on the listing card and detail page. Required.
    • features — bulleted list on the detail page.
    • website — link on the detail page.
    • youtube — embedded video on the detail page.
    • setup_minutes — "Setup time" on the detail page.
    • support — populates the Support tab.

    The plans field itself is optional, defaulting to an empty array for a free app, for example, but if given then each plan under it has its own listing fields:

    • id — a stable identifier for the plan (e.g. free, pro). Required.
    • price_in_cents — integer, 0 or more. Required.
    • app_store.title — the plan's name on the plan picker. Required.
    • app_store.description / app_store.features — optional store-facing copy shown on the plan picker.
    • features — internal feature flags ({id, enabled}) your app reads to know which capabilities are active for a given subscription — distinct from the display copy above.
    • most_popular — shows a "Most popular" pill on the plan picker.
    • paid_during_beta — paid plans are shown as free while your manifest's version is "beta". Set to true to keep this plan paid during beta. Defaults to false.

    Capabilities

    Each section below covers one thing your app can do inside Booqable: Tracking Scripts, Theme Blocks, Delivery Carriers, Payment Options, Embedded Pages, and Sidebar Frames. User Framework sits alongside them, but it isn't something you pick on its own. It's the JavaScript API shared by Tracking Scripts and Theme Blocks.

    Read only the sections relevant to what you're building. A real app commonly combines more than one, for example a payment app that also embeds a settings page.

    Tracking Scripts

    Tracking scripts let your app inject JavaScript into every storefront page — useful for analytics, marketing pixels, and similar integrations.

    // booqable.json
{
  "tracking_script": {
    "template": { "asset": "templates/index.js.liquid" }
  }
}

    Only JavaScript is allowed: the referenced template must be a Liquid file that renders to valid JavaScript. It is inlined into the page inside a load handler and is not validated, so a syntax error will break your script. Declarations at the top level are not global, so attach anything other code needs to window.

    Merchant-entered values (like an API key) come from a configuration_page form field, not a manifest key — see Configuration. Whatever the merchant enters is available in your template as a variable named after the field, e.g. const apiKey = '{{ api_key }}'.

    Your script only renders once the app is installed and configured, so if you have required form fields, nothing is injected until the merchant has saved them.

    Inside your template, use the User Framework to hook into storefront events (viewProduct, addToCart, checkout steps, ...) and to register for cookie consent.

    If your script sets cookies, register it with Booqable.registerApp so Booqable can gate it behind visitor consent. One real caveat: this only actually gates anything if the merchant has enabled the cookie notice in their theme. If they haven't, onConsent fires automatically for every visitor with no interaction at all — design your integration to tolerate either case.

    Example

    // templates/index.js.liquid
Booqable.registerApp('marketing', {
  name: "Google Analytics",
  domain: "googletagmanager.com",

  init: function () {
    window.dataLayer = window.dataLayer || []
    window.gtag = function () { window.dataLayer.push(arguments) }
    window.gtag('consent', 'default', { ad_storage: 'denied', analytics_storage: 'denied' })
    window.gtag('js', new Date())
    window.gtag('config', '{{ api_key }}')
    Booqable.loadScript('https://www.googletagmanager.com/gtag/js?id={{ api_key }}')
  },

  onConsent: function () {
    window.gtag('consent', 'update', { ad_storage: 'granted', analytics_storage: 'granted' })
  },

  onDeny: function () {
    window.gtag('consent', 'update', { ad_storage: 'denied', analytics_storage: 'denied' })
  }
})

    This example does its setup in init (always called on page load) and relies on GA4's own consent mode (gtag('consent', ...)) rather than gating inside onConsent/onDeny directly — a valid alternative when the third-party library you're wrapping has its own consent-aware mode.

    Theme Blocks

    Theme blocks let your app add custom content (widgets, forms, embeds) that merchants place into their website via the theme editor.

    // booqable.json
{
  "theme_blocks": [
    {
      "name": "Newsletter Signup",
      "template": { "asset": "templates/newsletter-signup.liquid" },
      "allowed_sections": ["app"],
      "settings": {
        "title": { "type": "text", "label": "Title", "default": "Subscribe to our newsletter" }
      }
    }
  ]
}
    • name: display name shown in the theme editor.
    • template: a Liquid template, rendered as HTML wherever the merchant places the block.
    • allowed_sections: required. The section types the block can be placed in: header, footer, or app (body sections). The block only appears in the theme editor's picker for those sections.
    • cookies_required: shows a notice in the theme editor that this block needs visitor cookie consent. It does not stop the block from rendering. To gate your scripts, register with Booqable.registerApp (see below).
    • settings_iframe_url: embeds a full iframe in the website editor's sidebar for this block's settings, instead of the declarative settings below (see Settings frame).
    • settings: declarative sidebar controls, keyed by name (see below).

    Settings types

    • text / textarea: single- or multi-line text input.
    • number: numeric input (min/max/step).
    • color: color picker.
    • checkbox: boolean toggle.
    • header: a section-divider label in the sidebar (uses content).
    • divider: a plain visual divider, no label.

    Each setting's value is available in your template as a Liquid variable named after the setting key (e.g. a height setting renders as {{ height }}).

    Merchant-entered global values (like an API key shared across every block instance) come from a configuration_page form field, not a manifest key — see Configuration. Whatever the merchant enters is available in your template as a variable named after the field, e.g. const apiKey = '{{ api_key }}'.

    Your block only renders once the app is installed and configured, so if you have required form fields, it won't appear until the merchant has saved them.

    If your block sets cookies, register it with Booqable.registerApp (see User Framework) so Booqable can gate it behind visitor consent. Same real caveat as tracking scripts: this only gates anything if the merchant has enabled the cookie notice in their theme. If they haven't, onConsent fires automatically with no visitor interaction. Design your integration to tolerate either case.

    Each block instance gets a unique app_id variable during rendering, useful for scoping CSS or JS to that specific instance:

    <div id="{{ app_id }}">
  <style>#{{ app_id }} .widget { /* ... */ }</style>
</div>

    Settings frame

    // booqable.json
{
  "theme_blocks": [
    {
      "name": "Reviews",
      "template": { "asset": "templates/reviews.liquid" },
      "allowed_sections": ["app"],
      "settings_iframe_url": "https://my-app.com/blocks/settings"
    }
  ]
}

    A settings frame replaces the declarative controls with a page of your own, filling the editor's sidebar. It runs under the Frames rules, and can't ask for any browser feature.

    Its URL isn't signed: Booqable adds no company or employee, so your page gets no proof of who is editing. It adds the block's text, number and true/false settings as query params, along with block_id, block_template and block_position, which identify the block.

    // in your settings frame
window.parent.postMessage({
  eventName: "SET_APP_BLOCK_SETTINGS",
  payload: { newSettings: { widget_id: "abc123" } }
}, "*")

    Post SET_APP_BLOCK_SETTINGS to change the block's settings: Booqable then reloads your frame with the new settings in its URL, so save anything else the page holds first. Post REFRESH_PAGE_PREVIEW to reload the editor's preview. These are the only messages a settings frame can send.

    User Framework

    The User Framework is a client-side JavaScript API, available as window.Booqable inside your Tracking Scripts and Theme Blocks templates. It doesn't apply to any other capability.

    Registering your app

    Booqable.registerApp('marketing', {
  name: "My App",
  domain: "example.com",

  init: function () {
    // Always runs on page load, regardless of consent.
  },

  onConsent: function () {
    // See "Consent gating" below: not guaranteed to run.
  },

  onDeny: function () {
    // See "Consent gating" below: not guaranteed to run.
  }
})

    Your template's top-level code runs with or without registerApp. In a theme block it runs as the page is parsed. In a tracking script it runs on the window load event, since the script is wrapped in a load handler. What registerApp actually gets you is a structured init callback that fires on the window load event, plus the onConsent/onDeny consent hooks below. If your script doesn't need to react to consent, you don't need registerApp at all. Call registerApp synchronously at the top level of your template. Registering later, for example inside a timeout or a callback, won't get init.

    The first argument is a category: marketing or essential. In practice almost every real app registers as marketing. The two categories aren't symmetric (see below), and essential is rarely used.

    Consent gating

    onConsent/onDeny are meant to gate cookie-setting behind the visitor's choice, but whether they fire at all depends on a setting the merchant controls, not something your app can see or influence:

    • If the merchant has the cookie notice enabled in their theme, onConsent/onDeny fire for marketing-category apps as the visitor accepts, denies, or changes their choice. essential-category apps never get onConsent/onDeny called in this case at all, only init runs for them.
    • If the merchant has not enabled the cookie notice, onConsent fires automatically for every registered app regardless of category, on every page load, with zero visitor interaction. onDeny is never called in this case.

    Practical implication: don't assume onConsent/onDeny reflect real, deliberate visitor consent. A merchant without the cookie notice enabled effectively grants blanket consent to every app on every page load. If your integration has real compliance requirements, treat this as a merchant configuration issue to flag, not something your app code can enforce on its own.

    Landing params

    When a visitor lands on the store with query params, Booqable saves them and adds them to cart and checkout links. That way a script that only loads after consent, or one running on the checkout's domain, can still read a click ID from the current URL.

    Declare the params your script reads in registerApp:

    Booqable.registerApp('marketing', {
  name: "My App",
  tracking: {
    landingParams: [
      { clickIdParam: 'myref', extraParams: ['mysub'] } // ?myref=123&mysub=newsletter
    ]
  }
})
    • clickIdParam: the param carrying the click ID. It's kept for 30 days.
    • extraParams: params that belong to that click, like a sub-ID. They're only forwarded together with the click they arrived with, so a new click never carries an older click's extras.

    Links to another domain (such as the checkout of an embedded store) get the saved params for up to 30 days. Links on the same site only get them during the visit they arrived in, except well-known ad click IDs such as gclid, which are kept there for 30 days too.

    Booqable.captureLandingParams

    Once your script has stored the click ID itself, for example in a cookie, call this so Booqable stops adding your declared params to links on the same site:

    Booqable.captureLandingParams("My App") // the name you passed to registerApp
    • It applies to your declared params that are in the current page's URL.
    • If several apps declare the same param, it's captured once all of them have called this.
    • It's optional. Params of apps that never call it keep being forwarded.
    • Call it only once the click is actually recorded. Calling it right in onConsent, before your library has loaded, can lose the click if the visitor leaves the page first.

    Links to another domain are not affected.

    Events

    Booqable.on('addToCart', function (data) {
  // data: { value, currency, items: [{ item_id, item_name, quantity, price }] }
})

Booqable.on('completed', function () {
  // no argument, read Booqable.cartData instead
})

    Available events: viewProduct, addToCart, removeFromCart, information, payment, completed, page-change.

    Only viewProduct, addToCart, and removeFromCart receive a data argument directly. Every other event fires with no argument at all, so read Booqable.cartData instead.

    page-change fires once per checkout page load (information, payment, completed). It does not fire on ordinary storefront navigation (home, product, listing, or static pages).

    Booqable.cartData

    Only available in the checkout events (information, payment, completed). Your app should only read it, never assign to it. It includes:

    cartId, orderId, orderNumber, currency, coupon, couponDiscount, deposit, toBePaid, totalDueLater, grandTotal, grandTotalWithTax, tax, deliveryPrice, items, email, name.

    Utilities

    • Booqable.loadScript(url) / Booqable.unloadScript(url): load or remove an external script, deduplicated by exact URL.
    • Booqable.jQuery(callback): runs callback once jQuery is available on the page as window.$, loading jQuery if needed. The version isn't guaranteed. If the theme already provides jQuery, you get that one.

    window.Booqable also exposes additional methods used internally by Booqable's own first-party integrations. These aren't part of this API and may change without notice, so stick to what's documented here.

    Example

    Booqable.registerApp('marketing', {
  name: "Example Tracker",
  domain: "example.com",

  onConsent: function () {
    Booqable.on('page-change', function () { /* ... */ })
    Booqable.on('viewProduct', function (data) { /* ... */ })
    Booqable.on('completed', function () {
      var total = Booqable.cartData.grandTotalWithTax
      // ...
    })
  }
})

    This pattern, subscribing to events only inside onConsent, is the safe default when the library you're integrating has no consent-aware mode of its own. If it does (as GA4's gtag('consent', ...) does), setting up in init and relying on the library's own gating is a valid alternative. See the Tracking Scripts example.

    Delivery Carriers

    Delivery carriers let your app offer custom shipping rates at checkout. Unlike tracking scripts or theme blocks, this isn't declared in the manifest at all. You register your carrier through the API once your app is installed.

    Registering a carrier

    // POST /api/4/app_carriers (request)
{
  "data": {
    "type": "app_carriers",
    "attributes": {
      "identifier": "my-carrier",
      "rates_url": "https://example.com/api/rates"
    }
  }
}

    POST /api/4/app_carriers, typically called right after your OAuth install completes.

    • identifier: a stable key for this carrier.
    • rates_url: where Booqable sends rate requests.
    • tax_category_id: optional, writable. Associates this carrier with a tax category used to calculate tax on its delivery rates.

    A carrier can also be updated later with PATCH/PUT /api/4/app_carriers/{id}, same attributes.

    Rate requests

    // POST {rates_url}?company_id=3b5e8f0c-2a41-4c7d-9e16-8d0f4a7b2c95&ts=1798761600&v=1&signature=… (request)
{
  "distance": 4.813,
  "distance_unit": "metric",
  "order_amount_in_cents": 300000,
  "origin_address": "Industrieweg 4,,1021 KZ,Amsterdam,Noord-Holland,Netherlands",
  "origin_coordinates": "4.9265,52.3912",
  "origin_location_id": "e1a4c2d8-5b37-4f90-8c6e-2d7b9a1f3e64",
  "origin_country": "NL",
  "destination_address": "Keizersgracht 123,,1015 CJ,Amsterdam,Noord-Holland,Netherlands",
  "destination_coordinates": "4.884,52.3752",
  "destination_zipcode": "1015 CJ",
  "destination_region": "Noord-Holland",
  "destination_country": "NL",
  "starts_at": "2026-12-04T09:00:00+01:00", // only through GET /api/4/order_delivery_rates
  "stops_at": "2026-12-06T17:00:00+01:00", // same
  "products": [ // same
    {
      "id": "9d2f6b1a-7c4e-4a85-b3d0-6e8f1c2a5b47",
      "title": "Party tent 6x3m",
      "price_in_cents": "300000.0",
      "quantity": 1.0
    }
  ]
}

    Whenever Booqable needs a delivery price, at checkout or in the back office, it sends a JSON POST to every active carrier's rates_url:

    • distance: driving distance from origin to destination, in the shop's distance_unit (metric for km, imperial for miles).
    • order_amount_in_cents: the order total before delivery and discounts, including tax if the shop's prices include it.
    • origin_address, destination_address: one comma-separated line: address lines, postcode, city, region, country.
    • origin_coordinates, destination_coordinates: "lng,lat", longitude first.
    • destination_zipcode, destination_region, destination_country: the destination's postcode, region and ISO alpha-2 country code.
    • origin_location_id, origin_country: the location Booqable picked to deliver from, which distance is measured from, and its country.
    • starts_at, stops_at, products: the rental period and product lines, each line with the product's id, title, quantity and price_in_cents (the line total, as a decimal string). Only filled in when rates are fetched through GET /api/4/order_delivery_rates; otherwise null, null and [].

    Every key is always present, with null for unknown values. Every _in_cents amount, in the request and in your response, is in hundredths of the main currency unit, whatever the currency: ¥3,000 is 300000.

    The request is signed; verify it before you answer. Booqable waits 3 seconds and doesn't retry. If you time out or don't answer with a valid JSON 200, Booqable skips your carrier. If you don't serve a request, for example because it's outside your coverage, respond with an empty data array.

    Responding with rates

    // your rates_url responds with this (response)
{
  "data": [
    {
      "id": "standard-shipping",
      "type": "delivery_rates",
      "attributes": {
        "carrier_id": "c4d9e7a1-6f2b-4e83-9a5c-1b8d3f0e7a26", // id returned when you registered the carrier
        "identifier": "Standard shipping",
        "label": "Standard shipping",
        "description": "Delivered between 9:00 and 17:00",
        "type": "flat",
        "price_in_cents": 2500,
        "range": "10 km",
        "minimum_order_amount_in_cents": null,
        "free_delivery_threshold_in_cents": 500000,
        "errors": []
      }
    },
    {
      "id": "express-shipping",
      "type": "delivery_rates",
      "attributes": {
        "carrier_id": "c4d9e7a1-6f2b-4e83-9a5c-1b8d3f0e7a26",
        "identifier": "Express shipping",
        "label": "Express shipping",
        "description": null,
        "type": "calculated",
        "price_in_cents": 4250,
        "range": "4.82 km",
        "minimum_order_amount_in_cents": 400000,
        "free_delivery_threshold_in_cents": null,
        "errors": ["under_minimum_order_amount"]
      }
    }
  ]
}

    Respond with Content-Type: application/json and a JSON:API list of the rates you offer for this request. Each rate has a string id, a type of delivery_rates, and these attributes:

    • carrier_id (required): the id Booqable returned when you registered the carrier.
    • price_in_cents (required): the delivery price.
    • identifier (required), label: the rate's name. Booqable shows identifier; an order placed at checkout is named after label. Send the same name in both.
    • description: optional text shown under the name.
    • type: flat or calculated. For a flat rate, Booqable shows range as "up to 10 km".
    • range: the distance to show, such as "10 km", or null to show none.
    • minimum_order_amount_in_cents: the minimum order for this rate, or null when there's none.
    • free_delivery_threshold_in_cents: the order amount from which this rate is free, or null when there's none. Return a price_in_cents of 0 yourself once order_amount_in_cents reaches it: the back office uses your price as is. Checkout shows the threshold to the customer until it's reached.
    • errors: why the rate can't be used for this order. Checkout shows a rate with errors but won't let the customer pick it, and Booqable avoids such rates when it picks one itself. Booqable doesn't check the minimum order: send under_minimum_order_amount when the order is below it, and checkout shows the customer the minimum amount.

    Keep each rate's id the same across requests: Booqable stores it on the order and uses it to find the rate again when the order changes.

    If the response isn't a JSON 200, or any rate lacks an id, attributes or the delivery_rates type, Booqable discards your whole response.

    Booqable passes your rates' attributes as they are to the shop's checkout and to API clients, for example through GET /api/4/order_delivery_rates, so don't put anything private in them.

    Uninstalling

    Uninstalling the app archives all of its carriers, removes their location links, and re-enables pickup at any location left without a carrier.

    Payment Options

    This capability allows your app to add custom payment options for users during checkout.

    Routes

    // booqable.json
{
  "base_url": "https://my-payments-app.com",
  "payments": {
    "routes": {
      "charge_url": { "relative": "/mypay/charge" },
      "cancel_charge_url": { "relative": "/mypay/charge/:id/cancel" },
      "authorization_url": { "relative": "/mypay/auth" },
      "capture_authorization_url": { "relative": "/mypay/auth/:id/capture" },
      "void_authorization_url": { "relative": "/mypay/auth/:id/void" },
      "refund_url": { "relative": "/mypay/refund" }
    },
    "pay_button": { "asset": "assets/pay-button.svg" }
  }
}

    Payment apps define their API routes under the payments.routes object of their booqable.json file. These routes tell Booqable where to send requests for different payment operations. Routes are relative to your manifest's base_url, or absolute URLs. pay_button is a separate, optional asset reference rendered as the clickable payment button in checkout.

    There are a total of 6 routes available:

    • charge_url
    • cancel_charge_url
    • authorization_url
    • capture_authorization_url
    • void_authorization_url
    • refund_url

    Configuration

    // POST /api/4/app_payment_options (request)
{
  "data": {
    "type": "app_payment_options",
    "attributes": {}
  }
}

    After a user installs your payment app, you must create a PaymentOption record using Booqable's Payment Options API endpoint. The PaymentOption enables Booqable to show new payment options in the UI using the routes configured in your app's booqable.json file. Users can then select your payment method during checkout, and Booqable will make signed requests to your app's endpoints.

    An empty attributes object is enough: name, identifier, and all 6 routes are copied from your manifest automatically.

    Create the PaymentOption right after your app exchanges its OAuth code for an access token (see OAuth), or once the user has provided any other settings your app needs.

    Tip: If you're using the Booqable App Rails engine, you can schedule the PaymentOption creation in a background job from the AppInstalledJob hook.

    There's no update endpoint for a payment option once created. To change a route later, archive and recreate it.

    Notes

    • Every request to your routes is signed: Booqable adds company_id, ts, v and signature to the route's query string, covering the body too. Verify the signature on every request. A retry (see below) resends the same signed request.
    • For charge_url and authorization_url flows, always update the payment status via the Booqable API before redirecting the customer back to the return_url. The callback page polls the payment status and will wait indefinitely if the status is never updated.
    • Even when a payment fails, update the status to failed before redirecting. Otherwise, the callback page polls indefinitely waiting for a status change.
    • Always store the booqable_id from the initial request. You'll need it to update the payment status later, especially for asynchronous payment processing.
    • The same booqable_id can arrive more than once. Handle it without failing, for example by returning the payment you already started for it.
    • Use the correct HTTP methods for the route:
      • charge_url, authorization_url, refund_url use POST to create new resources.
      • cancel_charge_url, void_authorization_url, capture_authorization_url use PUT to update existing resources.
    • If your route doesn't answer in time, Booqable resends the same signed request up to twice. Error responses aren't retried.

    Embedded Pages

    Embedded pages let your app present a full custom interface directly inside the Booqable UI, loaded in an iframe. This is the right choice when your app needs a dedicated page or dashboard of its own. For example:

    • Custom control surfaces and dashboards.
    • Complex configuration interfaces with custom validation.
    • Interactive setup wizards and onboarding flows.
    • Custom data visualization and monitoring.

    How embedded pages work

    // booqable.json
{
  "main_page": {
    "iframe": { "url": "https://my-app.com/dashboard" }
  }
}

    The url is either an absolute URL string, or a relative object like { "relative": "/dashboard" } that is resolved against your manifest's base_url (required for relative URLs). Booqable embeds it in an iframe and communicates with it over a postMessage protocol described below.

    The exact same mechanism is also available as a configuration_page.iframe, an alternative to declarative content blocks for your app's settings page. See Configuration for that specific field; everything below (the signed URL, the message protocol) applies identically to both. Both run under the Frames rules.

    Signed URL

    Booqable signs the iframe URL each time it loads it, adding company_id, employee_id (the employee viewing the page) and locale to its query string. Verify the signature before showing anything. Booqable only loads the page once the merchant has authorized your app through OAuth. Pages load before your app is configured, so show your own setup steps until then.

    A signature is only valid for 5 minutes, so verify it on the first load and keep your own session for the pages the iframe navigates to after that, without relying on cookies: browsers often block them in iframes. A short-lived token in your URLs works. Fetch anything else you need, such as the company's currency settings, through the API.

    Message protocol

    {
  eventName: "MESSAGE_TYPE",
  payload: {
    // Message-specific data
  }
}

    The iframe and Booqable communicate through a standardized postMessage protocol. All messages follow this structure and contain two fields: eventName and payload.

    Messages from iframe to Booqable

    SET_IFRAME_HEIGHT Sets the iframe height in pixels.

    window.parent.postMessage({
  eventName: "SET_IFRAME_HEIGHT",
  payload: {
    height: 600
  }
}, "*")

    SET_FLASH_MESSAGE Displays a success or error message to the user.

    window.parent.postMessage({
  eventName: "SET_FLASH_MESSAGE",
  payload: {
    type: "success", // or "error"
    message: "Configuration saved"
  }
}, "*")

    REFRESH_SUBSCRIPTION Requests Booqable to refresh the app subscription data.

    window.parent.postMessage({
  eventName: "REFRESH_SUBSCRIPTION",
  payload: {}
}, "*")

    GET_AVATAR Requests user avatar information for display in the iframe.

    window.parent.postMessage({
  eventName: "GET_AVATAR",
  payload: {
    id: "user_id",
    name: "User Name"
  }
}, "*")

    NAVIGATE Requests Booqable to navigate to a different page.

    The url must be a same-origin internal path (e.g. /app-store/installed). For security, Booqable resolves the URL against its own origin and ignores anything that points to a different origin, as well as javascript: and data: schemes. Use this to move the user between pages within the Booqable dashboard, not to redirect them to external sites.

    The optional reload flag controls how the navigation happens:

    • false (default): in-app navigation that keeps the single-page app loaded.
    • true: a full-page reload. Use this when all data must be refetched and any stale state cleared (for example after your app uninstalls itself and its subscription no longer exists).
    window.parent.postMessage({
  eventName: "NAVIGATE",
  payload: {
    url: "/app-store/installed",
    reload: false
  }
}, "*")

    Messages from Booqable to iframe

    SET_AVATAR Provides avatar information in response to a GET_AVATAR request.

    // Sent by Booqable to the iframe
{
  eventName: "SET_AVATAR",
  payload: {
    avatar: {
      id: "user_id",
      color: "#FF5733",
      initials: "UN",
      initialsColor: "#FFFFFF"
    }
  }
}

    Implementation example

    To the right is an example of a configuration interface.

    <!DOCTYPE html>
<html>
<head>
  <meta charset="utf-8">
  <title>App Configuration</title>
</head>
<body>
  <h1>Configure Your App</h1>
  <form id="settings-form">
    <label for="api_key">API Key</label>
    <input type="password" id="api_key" name="api_key" required>
    <div id="api_key_error" style="display: none; color: red;"></div>

    <button type="submit">Save Configuration</button>
  </form>

  <script>
    // Security: only accept messages from the window embedding this page, on
    // a Booqable origin. Match the domain or a subdomain of it, never just a
    // string suffix: "evilbooqable.com".endsWith("booqable.com") is true.
    const ALLOWED_DOMAINS = ['booqable.com'];

    function isValidOrigin(origin) {
      try {
        const hostname = new URL(origin).hostname;
        return ALLOWED_DOMAINS.some(domain => hostname === domain || hostname.endsWith('.' + domain));
      } catch {
        return false;
      }
    }

    function showError(fieldId, message) {
      document.getElementById(fieldId + '_error').textContent = message;
      document.getElementById(fieldId + '_error').style.display = 'block';
    }

    function adjustHeight() {
      window.parent.postMessage({
        eventName: 'SET_IFRAME_HEIGHT',
        payload: { height: document.body.scrollHeight }
      }, '*');
    }

    // Listen for messages from Booqable
    window.addEventListener('message', function(event) {
      if (event.source !== window.parent || !isValidOrigin(event.origin)) return;
      if (typeof event.data !== 'object' || event.data === null) return;

      if (event.data.eventName === 'SET_AVATAR') {
        console.log('Received avatar:', event.data.payload.avatar);
      }
    });

    // Handle form submission
    document.getElementById('settings-form').addEventListener('submit', function(e) {
      e.preventDefault();

      const apiKey = document.getElementById('api_key').value.trim();
      if (!apiKey) {
        showError('api_key', 'API key is required');
        return;
      }

      // Save configuration (replace with actual API call)
      setTimeout(() => {
        // Notify Booqable of success
        window.parent.postMessage({
          eventName: 'SET_FLASH_MESSAGE',
          payload: {
            type: 'success',
            message: 'Configuration saved'
          }
        }, '*');

        window.parent.postMessage({
          eventName: 'REFRESH_SUBSCRIPTION',
          payload: {}
        }, '*');
      }, 1000);
    });

    // Adjust height on load
    window.addEventListener('load', adjustHeight);
  </script>
</body>
</html>

    Sidebar Frames

    Sidebar frames let your app show a panel in the sidebar of an order, a customer or a product in the Booqable back office, about the record being viewed. For example, a delivery app can show the delivery status of the order the employee is looking at.

    Adding a panel

    // booqable.json
{
  "order_page": {
    "sidebar_frame": { "url": { "relative": "/panels/order" } }
  }
}

    Each of order_page, customer_page and product_page takes one sidebar_frame, a Frame like any other app page, so an app has at most one panel per sidebar. The panel runs under the Frames rules, can ask for permissions like any frame, and needs the same response headers.

    Panels sit below Booqable's own panels, in alphabetical order by app name. Employees can reorder and collapse panels, so don't rely on your panel's position.

    What the panel receives

    GET https://my-app.com/panels/order?company_id=…&employee_id=…&locale=en&order_id=…&ts=1798761600&v=1&signature=…

    Booqable signs the panel URL each time it loads it, adding:

    • company_id: the company the record belongs to.
    • employee_id: the employee viewing the record.
    • locale: the employee's language.
    • order_id, customer_id or product_group_id: the record being viewed, depending on the sidebar.

    Verify the signature before showing anything. Booqable only loads the panel once the merchant has authorized and configured your app. Until then the panel says "This app is not set up yet." and links to your app's page in Booqable. If the URL breaks the frame URL rules, it says "This app is unavailable."

    Sizing the panel

    // in your panel
new ResizeObserver(() => {
  window.parent.postMessage({
    eventName: "SET_IFRAME_HEIGHT",
    payload: { height: Math.ceil(document.documentElement.getBoundingClientRect().height) }
  }, "*")
}).observe(document.documentElement)

    The panel stays hidden until your page reports its height, so post SET_IFRAME_HEIGHT once it loads and again whenever its height changes. Booqable caps the height at 1000 pixels. It's the only message a panel can send.

    If no height arrives within 10 seconds, the panel says "This app did not respond." until one does. Panels load even when an employee has collapsed them, and reload with a freshly signed URL when an employee reorders them.

    Staying signed in

    A signature is only valid for 5 minutes, so anything that loads your panel's URL again later, such as a link, a form or a reload, needs a session of your own. Verify the signature on the first load, then carry a short-lived token in your URLs: browsers often block cookies in iframes.

    Only the signed first load proves locale and the record id. Once you've moved on to your own session, treat them as ordinary params.

    Panels are shown to every employee who can view the record, but a session started from a panel reaches the rest of your app too. Before showing or changing anything sensitive, check the employee's permissions through the API. Keep the session token out of URLs you hand to other services, such as a callback URL a merchant pastes into a third-party dashboard.

    Configuration

    Every app's settings page is built one of two ways: declarative content blocks, or an embedded iframe. Plan pricing and locale files are also covered here.

    Content blocks

    // booqable.json
{
  "configuration_page": {
    "content": [
      {
        "type": "Form",
        "title": { "localization_key": "form.title" },
        "fields": [
          { "name": "api_key", "type": "text", "label": { "localization_key": "form.api_key.label" }, "required": true }
        ]
      }
    ]
  }
}

    Content blocks let you declaratively define the content of your settings page. If your app only needs a few simple fields, this is the way to go.

    Block types

    • Banner: a heading, body text, and an optional link (rendered as a button with display_as_button: true). A nature style: neutral (default), info, or warning.
    • Form: renders a settings form, saved to App::Subscription#settings_values. The saved values are also available in your template as variables named after the field, e.g. const apiKey = '{{ api_key }}'. The form has a title and preamble (body text above the fields). Each field has a name, type, label, and optionally required, description, placeholder, min/max/step (for number/range), or options/multi (for select).
    • Guide: ordered steps, each with a title, optional text, and optional image. Used for step-by-step onboarding.

    Field types for Form: text, textarea, password, email, phone, number, range, color, code, contentEditor, datepicker, select, checkbox, checkboxGroup, radioGroup, buttonGroup.

    Any block can be shown conditionally with if: configured (only once the app is configured), unconfigured (only until then). An app counts as configured once all of its required form fields have a value, which is immediately if it has none. If omitted the block is always shown.

    Embedded settings page

    configuration_page.iframe replaces content blocks with a full embedded page, using the exact same mechanism (manifest shape, signed URL, postMessage protocol) as Embedded Pages. See that section for the details.

    Status message

    // booqable.json
{
  "status": {
    "dynamic": { "endpoint": { "relative": "/status" } }
  }
}

    Your app can show a live status message, such as "Last synced 5 minutes ago", on its page in the App Store. Booqable fetches the status endpoint from the employee's browser with a GET request, signed like an embedded page's URL, and without cookies. So the endpoint must:

    • verify the signature on every request
    • allow any origin with Access-Control-Allow-Origin: *, since the back office answers on more than one host
    • answer with a short plain-text message

    Booqable only asks once your app is configured and has no open issues. If the endpoint fails or takes longer than 5 seconds, Booqable shows its own message instead.

    Plans

    Plan pricing and store-facing copy are declared directly in booqable.json's plans array. See App Store Listing for the field reference. There's no separate plans file.

    Locale files

    // hardcoded
{ "title": "Gizmo App" }

    // localized
{ "title": { "localization_key": "app.title" } }

    A lot of the strings in booqable.json (titles, descriptions, labels, banner text, and so on) accept either a hardcoded value, or a reference to a translated string.

    Once you reference a localization_key, the actual string lives in a locale file instead: one YAML file per locale (see App Manifest).

    # config/locales/en.yaml
en:
  app:
    title: "Gizmo App"
    description:
      short: "A simple app to manage your gizmos."
      long: "Manage your gizmos, and delight your customers with new ones every month."
  form:
    api_key:
      label: "API Key"

    // booqable.json
{
  "app_store": {
    "title": { "localization_key": "app.title" }
  }
}

    There's no fixed schema inside, as long as the root key matches the locale code (e.g. en, pt_BR). The nested key path below that is entirely up to you: whatever localization_key you reference must resolve to a matching key in your locale file. A common convention, matching the schema's own examples, is to namespace by section.

    If a locale is missing a key your manifest references, provisioning fails with a validation error.

    Booqable Interop

    The sections below only apply if your app has its own backend: OAuth lets it call Booqable's API on a user's behalf, Signed requests lets it check that a request really comes from Booqable, Frames covers the rules its pages run under inside Booqable, and Webhooks let it react to events without polling.

    OAuth

    Booqable apps can use OAuth authentication to securely connect with Booqable's API on behalf of the user, without requiring them to share their credentials directly.

    How OAuth works in Booqable apps

    When an app has OAuth authentication enabled, Booqable handles the OAuth flow on behalf of the app:

    1. The user clicks to install the app.
    2. Booqable shows the user an in-app dialog listing the permissions (scopes) your app is requesting, and asks them to grant access.
    3. If access is granted, Booqable redirects the user's browser to your app's redirect_url with an authorization code.
    4. Your app exchanges the authorization code for an access and refresh token, and can then make API calls to Booqable's API.

    Configuring OAuth in your app

    // booqable.json
{
  "base_url": "https://my-app.com",
  "oauth": {
    "redirect_url": "/oauth/callback",
    "scopes": ["full_access"]
  }
}

    To enable OAuth for your app, configure the oauth object in your booqable.json file.

    • redirect_url: the path Booqable redirects to after authorization. A relative path, prefixed with your app's base_url.
    • scopes: the OAuth scopes your app requests. Currently the only scope available is full_access.

    Signed requests

    Booqable signs these requests and iframe URLs with your app's OAuth client secret. Verify the signature before you trust anything in them.

    • Delivery carrier rate requests
    • calls to your payment option routes
    • embedded pages, including a configuration_page.iframe
    • sidebar frames
    • the status message endpoint

    Theme block settings iframes aren't signed. Webhook deliveries carry a token query param instead: an HS256 JWT signed with your client secret that expires after 10 minutes.

    Signed params

    POST https://example.com/api/rates?company_id=7c1f0a52-3b9e-4d6a-8e24-5f2a9c3b1d70&region=eu&ts=1798761600&v=1&signature=15eb8124970543dc99cdf437ddd0b2c63c351abb9adb3eab94af7b13bc2fabe2

    Booqable adds these query params to the URL you configured, keeping the params it already has (region=eu in the example), and sorts them by name:

    • company_id: the company the request is for. Some requests add more context params; each capability lists its own.
    • v: the signing version, currently 1.
    • ts: when Booqable signed the request, in Unix seconds.
    • signature: the HMAC described below, always last.

    Every other param in the query string, including your own, is covered by the signature. Your URL can't already contain a param Booqable adds or repeat a param, and a + in it is read as a space.

    Verifying a request

    require "openssl"
require "digest"

MAX_AGE = 300 # seconds

def verify!(method:, path:, raw_query:, body:, secret:, now: Time.now)
  pairs = raw_query.to_s.split("&").reject(&:empty?).map do |pair|
    key, value = pair.split("=", 2)
    [decode(key), decode(value.to_s)]
  end

  keys = pairs.map(&:first)
  raise "repeated param" if keys.uniq.size != keys.size

  params = pairs.to_h
  raise "unsupported version" unless params["v"] == "1"
  raise "stale" unless params["ts"].to_s.match?(/\A\d+\z/) &&
    (now.to_i - params["ts"].to_i).abs <= MAX_AGE

  query = pairs
    .reject { |key, _| key == "signature" }
    .map { |key, value| [encode(key), encode(value)] }
    .sort_by(&:first)
    .map { |key, value| "#{key}=#{value}" }
    .join("&")

  message = ["v1", method, path, query, Digest::SHA256.hexdigest(body)].join("\n")
  expected = OpenSSL::HMAC.hexdigest("SHA256", secret, message)
  signature = params["signature"].to_s

  unless expected.bytesize == signature.bytesize &&
      OpenSSL.fixed_length_secure_compare(expected, signature)
    raise "bad signature"
  end

  params.except("signature", "v")
end

# Percent-decodes only; "+" stays a "+".
def decode(component)
  component.b.gsub(/%\h\h/) { |escape| escape[1, 2].hex.chr }.force_encoding(Encoding::UTF_8)
end

# Encodes every byte except A-Z, a-z, 0-9, "-", ".", "_" and "~".
def encode(component)
  component.b.gsub(/[^A-Za-z0-9\-._~]/n) { |byte| format("%%%02X", byte.ord) }
end

    To verify a request:

    1. Read the raw query string as it arrived, not your framework's parsed params, which may drop repeated keys, decode + as a space, or reorder params.
    2. Split it on &, then each pair on the first =, and percent-decode keys and values.
    3. Reject the request if any key appears more than once, if v isn't 1, if signature is missing, or if ts is more than 5 minutes away from your clock, in either direction.
    4. Build the canonical query: every pair except signature, keys and values percent-encoded as in RFC 3986 (every byte except A-Z a-z 0-9 - . _ ~, as uppercase %XX), sorted by the encoded key in byte order, joined as key=value with &.
    5. Build the message from these five lines, joined by \n with no trailing newline:
      • v1
      • the HTTP method in uppercase, such as GET or POST
      • the request path as sent, still percent-encoded, without the query string; / if it's empty
      • the canonical query
      • the SHA-256 of the raw request body, in lowercase hex. An empty body, as on every GET, hashes the empty string.
    6. Compute the HMAC-SHA256 of the message with your app's OAuth client secret, in lowercase hex, and compare it with signature in constant time.

    The body is part of the signature, so hash the bytes you received, before parsing them as JSON.

    A signature proves the request came from Booqable within the last 5 minutes. It doesn't stop the same request from being sent twice within that time, so make the endpoints it reaches safe to repeat. A valid signature also doesn't mean every param you need is there, so check that company_id is present before you use it. Keep signature out of your logs.

    Frames

    Booqable shows your app's pages in iframes: embedded pages (including a configuration_page.iframe), sidebar frames, and theme block settings. Every one of them runs under the rules below.

    Sandbox

    Every frame is sandboxed. Scripts, forms and popups work, and the page keeps its own origin. The main things that don't:

    • Native dialogs. alert(), confirm() and prompt() are blocked, and confirm() always returns false. Show your own dialog inside the page instead, such as a <dialog> element.
    • Navigating Booqable's tab. A link or form with target="_top" is blocked. An embedded page can send Booqable to one of its own pages with the NAVIGATE message.

    Popups aren't sandboxed, so run flows that need a whole tab, such as connecting a third-party account with OAuth, in a popup. When the flow ends, close the popup and refresh your frame.

    Browser features

    // booqable.json
{
  "configuration_page": {
    "iframe": {
      "url": { "relative": "/settings" },
      "permissions": ["clipboard-write"]
    }
  }
}

    Frames can't use the camera, microphone, geolocation, payments, screen capture, USB devices or fullscreen, and can't write to the clipboard. A frame that needs clipboard writes, for a copy button, asks for it with permissions, as in the example.

    clipboard-write is the only feature a frame can ask for on any Frame (for now). Theme block settings frames can't ask for it. Some browsers refuse clipboard writes in frames anyway, so fall back to document.execCommand("copy"), and only tell the user it was copied when a copy really happened.

    Referrer

    Frames load without a referrer: your pages get no Referer header, and document.referrer is empty.

    Response headers

    Content-Security-Policy: frame-ancestors https://*.booqable.com
Referrer-Policy: no-referrer

    Send these headers with every page Booqable embeds, so only Booqable can embed it and a signed URL doesn't leak to the sites your page links to. Keep signature and any session token of yours out of your logs.

    Frame URLs

    Booqable shows "This app is unavailable." instead of a frame it won't load. A frame URL must use https, have a plain ASCII host (use punycode for other characters), and have no credentials or fragment. It can't point at the merchant's own Booqable back office, and a signed frame URL can't already contain a param Booqable adds.

    Messages

    // in your frame
window.parent.postMessage({
  eventName: "SET_IFRAME_HEIGHT",
  payload: { height: 320 }
}, "*")

    A frame talks to Booqable with window.parent.postMessage. Each kind of frame accepts its own messages:

    • Embedded pages: SET_IFRAME_HEIGHT, SET_FLASH_MESSAGE, REFRESH_SUBSCRIPTION, GET_AVATAR and NAVIGATE, described in Message protocol.
    • Sidebar frames: SET_IFRAME_HEIGHT only, described in Sizing the panel.
    • Theme block settings: SET_APP_BLOCK_SETTINGS and REFRESH_PAGE_PREVIEW, described in Settings frame.

    Booqable ignores, without an error:

    • a message that isn't an object of the form { eventName, payload }, such as a JSON string
    • a message from any window other than the frame itself
    • a message from an origin other than the origin of the frame's URL, for example after the frame redirected to another domain

    Webhooks

    Apps can subscribe to webhook events to receive real-time notifications when certain actions occur in Booqable. This allows your app to respond to user actions and maintain synchronization with the platform.

    To learn more about how to use webhooks see the Webhook Endpoints documentation.

    Available app events

    There are four webhook events specifically related to app lifecycle:

    app.installed

    Triggered when a user installs your app from the Booqable App Store.

    app.configured

    Triggered every time the subscription is saved while the app is configured, not only on the one-time transition into being configured. If a merchant edits already-configured settings again later, this fires again.

    app.plan_changed

    Triggered when a user upgrades or downgrades their app subscription plan.

    app.uninstalled

    Triggered when a user removes your app from their Booqable account.
